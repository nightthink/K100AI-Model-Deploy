# 标准性能测试（唯一口径）

**本仓只有一个性能基准脚本：`tests/standard_load.py`。**
所有线（01 / 02 / 09 / 10 / 11 / 12 / 13 …）的性能数字都必须出自它，换线只改 `--port`。
任何其它脚本都不是标准测试，其产出不得写入 README 当性能值。

```bash
python3 tests/standard_load.py --port 8101 --cycles 2 --out ~/perf/01
python3 tests/standard_load.py --port 8113 --cycles 2 --out ~/perf/13    # 换线只改端口
```

## 一、负载口径（用户 2026-09-17 确认，唯一权威）

| 项 | 值 |
|---|---|
| 输入 | 45K – 350K token，**均值 160K** |
| 输出 | 500 – 4K token，**均值 800** |
| 输入 cache 命中率 | **均值 95%，最小 85%** |
| 周期切换 | 涨到 350K 后，切换到 **~70K 的全新前缀**（全新 = 必然未命中） |

## 二、产出：四个指标的矩阵

**TTFT、prefill 速率、decode 速率、E2E 时间** —— 按「输入深度 × 输出规模」两维分桶，
每格给出中位数与样本数。

- 输入分档：45–80K / 80–120K / 120–180K / 180–250K / 250–320K / 320–350K
- 输出分档：500–900 / 0.9–1.5K / 1.5–2.5K / 2.5–4K

另出两张表：周期切换（全新前缀）的未命中成本；以及**自证表**（见第四节）。

## 三、两个设计要点

**命中率是构造出来的，不是碰出来的。** 某轮命中率 = 上轮 prompt ÷ 本轮 prompt。
设上轮深度 P、本轮新增 d（上轮模型输出 + 本轮用户输入），则命中率 = P/(P+d)。
要 95% 就得 d = P × 0.05/0.95 ≈ **0.0526 × P** —— 70K 时每轮加约 3.7K、
160K 时加约 8.4K、350K 时加约 18.4K。脚本按此定增量，命中率因而稳定落在 95%；
每 7 轮按最小命中 85% 取一次大增量，覆盖真实负载的抖动。

**矩阵靠「定深扫输出」填满。** 若输出规模随轮次变化，它会与深度强相关，
矩阵格子必然打不满。故每到一个深度档，就在**同一深度**上连发四种输出规模的探针；
探针**不追加进对话历史**，深度因此不变、前缀仍命中，扫完再继续增长。

## 四、自证表：先验负载，再看数字

报告第一张表是自证表，列出**实际达成**的输入范围/输入均值/输出均值/命中率均值/
命中率最小值，并与上表目标逐项比对。**任一项不达标，则该次的性能矩阵一律不作数**
—— 说明测试没跑成这个负载，数字再好看也没有意义。

## 五、prefill 速率的两种口径

矩阵里的 prefill 速率 = **总输入 ÷ TTFT**，即用户实际感受：整个输入等了多久出首字。
在 95% 命中下这个值天然远高于「只算未命中部分」的速率，报告末尾同时给出后者备查。
**跨线比较时必须确认用的是同一口径。**

## 六、历史口径作废说明

压缩回40K、出300`）是**旧口径，已作废**，其数字不可与本标准测试的结果混用。

每次复现都靠人重读 README 手搓，这正是它必须被本脚本取代的原因。

最深约 45K token，够不到本负载的 350K 顶点；2026-09-17 曾被误当作标准测试跑掉四小时
机时，产出的数字与本口径无关。已从仓中删除（git 历史保留）。
