# HRRN 调度策略 · 从 0.5.20 回输到 0.5.12

上游 **#32911**（`[Scheduler] Add HRRN schedule policy`，合入 2026-09-08），
原生最早只在 **v0.5.20**（09-18 发布）。我方两线基座是 **0.5.12**。

**上游实测**：mean TTFT **−69%**、p99 −8%（vs FCFS，GLM-5.2 生产 trace）。

## 为什么这条能回输，而 v0.5.20 的多数好东西不能

它是**纯调度器逻辑** —— 只重排等待队列，不碰算子、不碰显存分配、不碰通信。
对比 v0.5.20 的 AMD 节约 50 条优化（含 6 条 `[AMD][DSv4]`），那些全部锁死在
gfx950/MI355X；本条与 GPU 架构无关，因此既跨平台也跨版本。

## 0.5.12 与上游的四处差异（**全部实测确认，非推断**）

| # | 上游 | 0.5.12 | 处置 |
|---|---|---|---|
| 1 | `r.num_matched_prefix_tokens` | 无此字段 | 用 `len(r.prefix_indices)`——LPM 在 0.5.12 自己就这么取，同一语义 |
| 2 | `arg_groups/fields/schedule.py` 注册 CLI | 无该目录 | 不必改：`server_args.py:4949` 的 `--schedule-policy` **没有 `choices=` 限制**，可直接传 `hrrn` |
| 3 | Enum 里已有 HRRN 成员 | `CacheAwarePolicy` 只有 lpm/dfs-weight | **必须真正注册 Enum 成员**。`_validate_and_adjust_policy` 走 `CacheAwarePolicy(policy)` 按 value 查找，只塞 `_value2member_map_["hrrn"]=None` 会返回 `None` 并在下游炸 |
| 4 | `calc_priority` 无返回值约定 | **返回 `bool`** | wrapper 必须透传返回值 |

## 调用方契约（缺了算法退化成按 rid 排序，上游 docstring 明示）

* Scheduler 维护单调递增 prefill token 计数器，每轮 `run_batch` 累加 `extend_num_tokens`
  （decode / prebuilt 批为 None 或 0，自然不计）
* 请求入队（`_add_request_to_queue`）时快照 `req.arrival_processed_tokens`

两者均以 wrapper 实现，**不改镜像内任何源码文件**。

## 用法

```bash
# 注入（在 sitecustomize 或启动前）
python3 -c "import patch_hrrn; print(patch_hrrn.apply())"
# 启用
--schedule-policy hrrn
```

# 第二条回输：RadixKey galloping match + offset 游标

上游 **#37324**（`[Perf] Walk the radix tree by offset instead of re-slicing token
storage`，合入 2026-09-03，ported from #36507），原生最早在 v0.5.20。

## ★ 实测发现：真正的大头不是 offset，是 match 的实现

进 0.5.12 镜像读源码才看到，`RadixKey.match` 是**逐 token 的 Python 循环**：

```python
i = 0
for a, b in zip(t0, t1):
    if a != b: break
    i += 1
```

上游同名方法早已是**指数搜索（galloping）+ 二分**，每轮一次 C 层切片比较。
对「95% 命中的长前缀」负载这是数量级差别 —— 命中 40 万 token 时，0.5.12 走
40 万次 Python 迭代，galloping 约 2·log₂(4e5) ≈ 37 次 C 层比较。
**这一条的收益比 offset 本身大得多**，故两者一并回输。

## 实测提速（0.5.12 镜像内，全命中前缀）

| 前缀长度 | 原生逐 token | galloping | 加速 |
|---|---|---|---|
| 1,000 | 0.06 ms | 0.017 ms | 4× |
| 50,000 | 3.04 ms | 0.550 ms | **6×** |
| 200,000 | 12.16 ms | 2.812 ms | 4× |
| 400,000 | 24.1 ms | 3.886 ms | **6×** |

## ★★ 三轮才对：page_size>1 的语义陷阱

前两版照抄上游的 `(m // page_size) * page_size`，都被对拍打回
（400 例差 15 个、2000 例差 62 个）。原因：

**0.5.12 原生在 `page_size>1` 时，返回值可以超过实际长度。**

```python
while i < min_len:
    if t0[i:i+ps] != t1[i:i+ps]: break
    i += ps
```

`n=3, ps=2` 全匹配时原生返回 **4**：i=2 时比较 `t0[2:4]` vs `t1[2:4]`，
Python 切片越界**自动截断**成单元素、相等 ⇒ i=4，循环退出。
即「末页只要截断后的残余相等，就整页计入」。上游把这个改掉了。

**回输原则：只换实现，绝不顺手改变对外行为。** 原生这个「超长返回」是否算 bug
交给上游去修；我方若在回输里变更，会牵连 `_match_prefix_helper` 中
`prefix_len` 与 `len(child.key)` 的比较、以及 value 张量的切片长度。
故最终版按原生规则逐位复刻，只把逐 token 比较换成 galloping。

## 验证（2026-09-19，0.5.12 镜像内一次性容器，RC=0）

```
[2] 对拍 2000 例（含 30% bigram、ps∈{1,2,64}）：不符 0
[3] match_at(offset) vs 原生 match(other[off:])：不符 0
[4] 提速见上表
```

bigram 模式必须覆盖——我方 01/13 线都开 NEXTN 投机，走的正是 bigram 路径。

## 未改的部分

`_split_node` 内部仍用 `key[split_len:].child_key(...)`。它在分裂路径上、
每次匹配至多走一次（走到即 break），非热点；改它会牵连正确性，不值得。

# 实机 A/B 结论（2026-09-20，01 线 TP4，标准负载各跑满 1 个完整周期）

## 臂 B（radix 回输）vs 臂 A（基线）：**端到端无可测收益**

A/B 各 59 行、34 条常态轮，六档样本齐整，同深度档比中位数：

| 深度 | n(A/B) | TTFT A→B | 比 | prefill A→B | 比 |
|---|---|---|---|---|---|
| 45–80K | 10/9 | 3.43→3.18s | 0.93× | 17,913→17,507 | 0.98× |
| 80–120K | 6/7 | 7.95→6.36s | 0.80× | 14,012→13,864 | 0.99× |
| 120–180K | 6/6 | 14.94→14.96s | 1.00× | 9,929→10,130 | 1.02× |
| 180–250K | 5/5 | 28.82→30.67s | 1.06× | 7,031→6,754 | 0.96× |
| 250–320K | 4/4 | 70.00→73.52s | 1.05× | 4,433→4,370 | 0.99× |
| 320–350K | 3/3 | 89.17→97.43s | 1.09× | 3,788→3,724 | 0.98× |

**prefill 六档全在 0.96–1.02×，即完全没变**；TTFT 在 ±9% 内无方向性摆动。

### 与 dry-run 的 6× 为何不矛盾

dry-run 量的是 `RadixKey.match` **单函数**（40 万 token 全命中 24.1ms → 3.9ms）。
端到端 TTFT 里，前缀匹配只占极小一块，绝大部分是 GPU 上的 prefill 计算。
**微观 6× 摊到宏观就消失了。** 这个量级估算本该在设计 A/B 之前就做。

⇒ **radix 回输保留**（正确性经 2000 例对拍、语义逐位复刻原生，无风险），
但**不应作为性能改进项宣称**。它的价值在深度更大、或前缀树更深的场景，
本负载下测不出来。

## 一次测量设计失误，记下来

首轮用 `--hours 0.42`（25 分钟），本意是省机时。但标准负载单周期实测约 70 分钟，
`--hours` 的语义是「到点不开新周期，但不腰斩正在跑的周期」——
A 臂侥幸跑完整周期（59 行），B 臂被截断在 265K（28 条常态轮、无 report.md）。

更坏的是我据此做了对比，得出「250–320K 档 B 比 A 慢 2.17×」的结论。
逐条一看才知：**B 在该档只有 1 条样本，恰是命中率 85% 的轮次**
（标准负载每 7 轮故意压到最低命中），而 A 的中位数取自 4 条里 3 条 95% 命中的。
拿 85% 单点比 95% 中位数——纪律 7（口径不一致）与纪律 15（单点无自证能力）
同时踩中。真正配对的是 A 的 263146（149.56s/85.2%）vs B 的 265935（152.25s/85.1%），
**两者基本相当**。

⇒ A/B 一律用 `--cycles 1`（跑满整周期就停），不用 `--hours` 猜时长。

## 结论

**两条回输在本负载下都没有性能收益，HRRN 在浅档还是负收益。**

* **radix**：prefill 六档 0.96–1.02×，TTFT ±9% 无方向性 ⇒ **无可测收益**
* **HRRN**：浅档 TTFT +53%（3.43→5.25s）、prefill −31%；深档持平 ⇒ **净负收益**

### HRRN 为什么在这里是负的（机制，不是拟合）

上游那个 **TTFT −69%** 测于 **GLM-5.2 生产 trace** —— 那类负载**队列里堆着大量请求**，
HRRN 靠重排让短任务插队，收益来自**减少排队等待**。

我方标准负载是**单流顺序压测**，队列里基本只有 1 个请求。
**没有队列就没有重排空间**；而 HRRN 每轮仍要跑 `_compute_prefix_matches` + 排序，
这份开销成了净成本，在 TTFT 本来就小的浅档最刺眼（3.43s → 5.25s，多出的
约 1.8s 正是它）。深档 TTFT 本身几十秒，开销被摊薄到看不见。

⇒ **这是负载形态不匹配，不是实现有问题。** HRRN 若要显出价值，需要有并发排队的负载。

## 最终处置

| 回输 | 正确性 | 端到端收益 | 默认 | 说明 |
|---|---|---|---|---|
| radix galloping+offset | ✓ 对拍 2000 例零不符 | 无（±2%） | **开** | 纯加速、语义逐位复刻原生，无风险；深树/更长前缀场景可能有价值 |
| HRRN 调度 | ✓ 5/5 请求 200 | **负**（浅档 TTFT +53%） | **关** | 需 `--schedule-policy hrrn` 显式启用；**仅在有并发排队的负载下才考虑** |

**不要为了「有进步」而含糊**：这轮回输的净结果是**两条都无收益**。
真正的产出是三条 —— 打通了从 0.5.20 回输到 0.5.12 的**方法**、
证实了海光侧无 0.5.20（整版升级无路可走）、以及下面这批教训。

## 冷启动污染排查（2026-09-21，回应光合社区 2364 的告警）

光合社区帖 2364「冷启动如何把 0.325% 伪装成接近三倍」指出：**B-A-B-A 交错 A/B
仍可能被污染**——四次新启服务，baseline 4.18/5.50 vs candidate 15.04/15.14 tok/s，
输出 10/10 逐字一致、failed=0，看似铁证，实为每个 baseline 进程都撞上**进程级冷路径**
（数分钟级）。原文结论：

> 「B-A-B-A 重复了污染，而不是消除了污染。」

**我方三臂 A/B 正是「每臂重新起服」这同一形态**，故必须自查。结果：**无污染**。

| 臂 | E2E 中位 | E2E 最大 | 最大/中位 |
|---|---|---|---|
| A | 53.0s | 212.9s | 4.0× |
| B | 56.8s | 222.0s | 3.9× |
| C | 55.9s | 217.6s | 3.9× |

三条证据：

1. **无数分钟级异常**。最长仅 ~4× 中位数；2364 的案例是**数分钟级**，量级不同。
2. **最慢请求在三臂中位置逐轮对应**：都是第 **#57**（深度 338–345K）、
   **#49**（277–283K）、**#45**（263–268K）。这是**深上下文本就慢**，不是冷启动伪影——
   若是冷路径，必出现在**开头**而非第 57 轮。
3. **每臂第 1 轮都是设计内的「全新前缀」**（命中 0%、TTFT 23–25s），
   且**不计入常态轮统计**；第一个常态轮（#2）TTFT 仅 1.32 / 2.39 / 3.79s，无冷路径特征。

同 seed 使三臂逐轮结构对应（相同轮次类型、相近深度），这正是对比有效的根据。

⇒ **radix 无收益、HRRN 浅档负收益的结论不受冷启动污染影响，成立。**

> 今后凡「每臂重新起服」的 A/B，一律加这一步排查：看 E2E 最大/中位倍数，
> 以及最慢请求**落在哪一轮**（开头 = 可疑，深档 = 正常）。
