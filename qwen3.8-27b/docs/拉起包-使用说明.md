# 拉起包 · 使用说明

一个包、一个脚本 `up.sh`，管全部动作：拉起 / 停止 / 重启 / 状态 / 日志 / 性能测试。

```bash
tar xzf q38-kit-01-*.tar.gz && cd q38-kit-01
bash up.sh                    # 拉起（一线一包：直接起该线）
```

## 一、六个动作

| 命令 | 作用 |
|---|---|
| `bash up.sh` | 拉起。体检 → S1 机器准备 → S1.5 补丁部署 → S2..S8 → 真实请求冒烟 |
| `bash up.sh status` | 看状态（含各实例端口/接口/容器/重启次数、阶段进展、重启待办） |
| `bash up.sh stop` | 停止（S9 清场） |
| `bash up.sh restart` | 重启（参数从容器实况还原，无需重报卡与端口） |
| `bash up.sh logs [-f]` | 看容器日志 |
| `bash up.sh benchmark` | **标准性能测试**（见第四节） |

## 二、同机起多个实例

**同一个包、同一个脚本，除参数外不改任何文件**：

```bash
bash up.sh GPUS=0,1,2,3 PORT=8101      # 实例一（沿用 @name）
bash up.sh GPUS=4,5,6,7 PORT=8102      # 实例二（名字自动派生为 …-8102）
```

模型若只占 2 卡，同法可在 8 卡机上起 4 个。未给 `NAME=` 时按端口派生实例名；
Triton 缓存按实例隔离（`$D/tritoncache-int8-$NAME`），互不干扰。

**端口就是实例句柄** —— 起服时给「哪几张卡 + 哪个端口」，之后一律用同一个端口指定：

```bash
bash up.sh status  PORT=8102      # 只看该实例
bash up.sh logs    PORT=8102      # 只看该实例日志
bash up.sh restart PORT=8102      # 只重启该实例，不影响其它
bash up.sh stop    PORT=8102      # 只停该实例，不误伤其它
bash up.sh stop                   # 不带端口 = 全停
```

## 三、状态契约（供上层调用者判断）

上层**不必解析人类可读文本**。每次动作都会打印一行机器可读状态：

```
STATE=<名> CODE=<码> MSG=<说明> [附加 k=v ...]
```

同时落盘到 `.state`（多实例为 `.state-<端口>`），供异步轮询。
命令的**退出码即状态码**。纯查状态、无任何副作用：

```bash
bash up.sh state                 # 单实例
bash up.sh state PORT=8102       # 多实例指定
```

### 全部状态

| 码 | STATE | 含义 | 上层该做什么 |
|---|---|---|---|
| 0 | `READY` | 拉起已成功 / 服务正常，等待命令中 | 继续；附加字段给出 `PORT`/`GPUS`/`ENDPOINT` |
| 1 | `FAILED` | 通用失败 | 看 `FIX=` 字段 |
| 10 | `NEED_REBOOT` | 补丁已部署，等待主机重启 | **重启后重跑同一条命令** |
| 11 | `NO_DOCKER` | docker 或启动程序未安装/不可用 | 装 docker 或给权限 |
| 12 | `NO_DRIVER` | 驱动未安装（`/dev/kfd`、`hycu`、`/opt/hyhal`） | 装驱动栈；**本包不装驱动** |
| 13 | `NO_MODEL` | 指定位置没有对应模型 | 放权重，或改 `MODELS_ROOT=` |
| 14 | `NO_IMAGE` | 镜像不在本机且获取失败 | 手工 pull 或配置镜像源 |
| 20 | `STARTING` | 正在拉起，状态正常，仍在等待 | **继续轮询**，别当失败 |
| 21 | `STARTING_BAD` | 正在拉起，但已出现异常迹象 | 看 `MSG` 里的症状，准备失败 |
| 22 | `START_FAILED` | 拉起已失败 | 看 `LOG=` 指向的日志 |
| 30 | `BENCH_RUNNING` | 正在 benchmark，仍未结束 | 继续轮询 |
| 31 | `BENCH_DONE` | benchmark 已结束 | 读 `REPORT=` 指向的报告 |
| 32 | `BENCH_INVALID` | **跑完但自证未达标 —— 数字不作数** | 别用这批数字；查为何没跑成该负载 |
| 40 | `SERVICE_ERROR` | 服务异常（非200 / OOM / Traceback / 5xx） | `MSG` 里给出具体表现 |
| 50 | `STOPPING` | 正在 stop，仍未结束 | 继续轮询 |
| 51 | `STOPPED` | 已完成停止，服务已停 | — |
| 60 | `NOT_FOUND` | 未找到指定实例（`PORT=` 解析不到） | 核对端口 |
| 61 | `AMBIGUOUS` | 同机多实例但未指定端口，**拒绝操作** | 补 `PORT=` 再来 |
| 62 | `PORT_BUSY` | 端口已被占用 | 换端口 |
| 63 | `GPU_BUSY` | 请求的卡已被其它实例占用 | 换卡组 |
| 64 | `PATCH_UNKNOWN` | 补丁字节与预期不符，**拒绝自动改写** | 人工确认偏移是否随驱动版本变了 |
| 65 | `ATTEST_FAILED` | 服务起来了但 S8 自证未过 | 看日志；冷启暖场后可重试一次 |
| 66 | `MODEL_INCOMPLETE` | 权重存在但不完整/校验不过 | 重新获取权重 |
| 67 | `KFD_RESIDUE` | 已停止但 KFD 仍有孤儿进程 | 确认无其它业务后**重启机器** |

### 两条要点

**`NEED_REBOOT`（10）优先于一切服务状态。** 内核模块补丁改的是磁盘上的 `.ko`，
运行中的驱动仍是旧的；未重启时即便服务起得来也不算数。
一律「改文件 → 重启机器」，**绝不 `rmmod`/`insmod` 重载**（会让 KFD 驱逐永久打摆）。
该状态同时落 `.reboot-required`，`status` 的「重启待办」栏也会显示。

**`BENCH_INVALID`（32）与 `BENCH_DONE`（31）必须分开看。** 跑完不等于跑对：
若自证表显示实际输入均值/输出均值/命中率对不上口径，说明测的是**另一种负载**，
这批数字不能当性能数据用。

## 四、标准性能测试

```bash
bash up.sh benchmark                              # 测在跑实例（端口自动取）
bash up.sh benchmark PORT=8102 CYCLES=2 OUT=/tmp/perf
```

负载口径（唯一权威）：**输入 45K–350K（均值 160K）／输出 500–4K（均值 800）／
输入 cache 命中率均值 95% 最小 85%／涨到 350K 后切 ~70K 全新前缀**。

产出 **TTFT / prefill 速率 / decode 速率 / E2E** 四个指标的「输入深度 × 输出规模」矩阵，
外加一张**自证表**：列出实际达成的输入均值、输出均值、命中率均值与最小值。
**自证表任一项不达标，该次性能数字一律不作数** —— 说明没跑成这个负载。

全部线用同一个脚本、同一口径，换线只改端口，因此各线数字可直接横向比较。
详见 `docs/标准性能测试.md`。

## 五、宿主机前提

本包**不安装驱动**。搬到新机器上需要宿主机自备：

| 前提 | 说明 |
|---|---|
| DCU 驱动栈 | `/dev/kfd`、`/dev/dri`、`/opt/hyhal`、hycu 驱动已绑 ≥4 张卡 |
| docker | 且当前用户可用（docker 组或 sudo NOPASSWD） |
| sudo | S1 要往宿主机装 sysctl/systemd 产物 |
| python3 / curl / xxd | xxd 用于内核补丁字节校验 |
| 镜像 | 见线内 `serve.sh` 的 `@image`；S2 会自动拉取 |
| 模型权重 | `MODELS_ROOT`（默认 `/data/models`）；S2 会自动获取 |

**驱动本身不装，但对已装驱动的补丁由本包自动部署**（见第三节退出码 10）。

## 七、新合同 · 四动作接口与恢复

> **状态：已在 01 线与 13 线的包中实现。** 规范条款见 `拉起包-设计要求.md`
> 第九节（R24–R38）。其余线仍按本文第一至六节使用。

### 7.1 四个动作

对外只有四个动作。**执行机制与资源判断归拉起包**，
调用方**不要**去解析 Docker、systemd 或宿主进程来推断状态。

```bash
bash up.sh start  MODEL=<path> GPUS=<set> PORT=<port>   # 快速触发，不等就绪
bash up.sh state  PORT=<port>                            # 无副作用，机器可读
bash up.sh stop   PORT=<port>                            # 定点停止
bash up.sh logs   LAUNCH_ID=<id>                         # 按启动生命周期取日志
```

### 7.2 推荐用法：先全部触发，再统一轮询

`start` **不等待就绪**（当前实现是同步等待，这是新旧差异最大的一处）。
建议顺序循环触发，全部触发完再统一轮询：

```bash
# ① 顺序触发（每条立即返回）
for cfg in "$M1 0,1,2,3 8101" "$M2 4,5,6,7 8102"; do
  set -- $cfg
  bash up.sh start MODEL="$1" GPUS="$2" PORT="$3"
done

# ② 统一轮询（无副作用）
while :; do
  for p in 8101 8102; do
    bash up.sh state PORT="$p"; echo "  exit=$?"
  done
  sleep 30
done
```

**不要用 `start` 探活** —— 它有副作用；探活只用 `state`。

### 7.3 实例身份：四项全等才算同一个

```
(realpath(model_path), 排序去重后的 GPU 集合, launch_mode, port)
```

* **模型**按 `realpath` 比 —— 软链、相对路径、结尾斜杠不影响判定
* **GPU** 排序去重后比 —— `4,5,6,7` 与 `7,6,5,4,5` 是同一集合
* **launch_mode** 只表达**执行机制** —— `docker` / `systemd` / `process`。
  它**不表达**引擎（sglang / vllm）、TP 规模、精度、投机算法或调优方案。
  **01 线与 13 线当前都是 `launch_mode=docker`**，两者在该字段上相同；
  它们的区别体现在模型路径、GPU 集合与端口上。

### 7.4 四项全等时会发生什么

| 既有状态 | `start` 的行为 |
|---|---|
| `READY` | **复用并返回成功**，不重建，`launch_id` 不变 |
| `STARTING` | **挂接原 `launch_id` 继续观察**，不新建、不打断 |
| `FAILED` | 清理**可证明属于该次失败的包自有残留**，**新建 `launch_id`** 重拉 |

> 与当前行为的差异：现在是「同名一律删掉重建」，不看参数、不分状态。

### 7.5 换端口

模型、GPU、`launch_mode` 相同、**只有端口不同**时：

```
① 先确认新端口可用  →  ② 定点停旧  →  ③ 按新端口拉起
```

**新端口不可用时不会停旧服务** —— 不会出现「既没起来新的、又把旧的弄没了」。

### 7.6 失败关闭：这五种情况会直接失败，且不会自动清理

| 情况 | 说明 |
|---|---|
| GPU 集合**相交但不完全相同** | 不会部分复用，也不会抢占 |
| **同 GPU 但模型不同** | 失败 |
| **同模型同 GPU 但 `launch_mode` 不同** | 失败 |
| 目标**端口被其它实例占用** | 失败 |
| **未知占用** | 失败，**需要人工干预** |

> 「未知占用」指无法证明归属的 GPU／端口／进程／实例。
> 拉起包**不会**去清理它——那可能是别人的生产服务。

### 7.7 标识与日志

| 标识 | 粒度 |
|---|---|
| `invocation_id` | **每次命令调用**一个 |
| `launch_id` | **每次实际启动生命周期**一个；复用与挂接**不**新建 |

日志为**标准 JSONL 事件流** + **最新状态快照**；`logs` 按 `launch_id` 读取。

### 7.8 Callback（可选，不配置就不调用）

两种目标任选其一：

```bash
# 本地脚本：事件 JSON 从 stdin 传入
CALLBACK=/path/to/hook.sh

# HTTP：POST，Content-Type: application/json
CALLBACK=https://agent.example/events
```

事件至少包含：

```json
{
  "schema_version": "1",
  "invocation_id": "...",
  "launch_id": "...",
  "state": "STARTING",
  "code": 20,
  "reason": "waiting_ready",
  "sequence": 3,
  "observed_at": "2026-09-22T01:23:45+08:00",
  "identity": { "port": 8101, "gpus": "0,1,2,3", "launch_mode": "docker" }
}
```

**三条语义要记住：**

1. **有界超时** —— 不会因为 Callback 慢而拖住拉起
2. **失败不改变拉起结果** —— Callback 打不通，`start` 的退出码不变
3. **不自动重试** —— `state` 查询是最终事实兜底

**不会出现在事件里的**：主机名／IP／凭据、模型绝对路径原文、容器完整启动命令、
环境变量原文、日志正文。

### 7.9 恢复（Resume）：部分成功、部分失败时

按实例逐个 `state`，再按下表分派：

| `state` 返回 | 处理 |
|---|---|
| `READY` + 身份四项全等 | **跳过，不触碰** |
| `READY` + 身份不同 | **告警**，交人或策略决定；需替换则先 `stop` 再 `start` |
| `STARTING`(20) | **继续轮询**，设上限（01 线约 5 分钟就绪、13 线约 8 分钟，上限按最慢的取） |
| `STARTING_BAD`(21) | **按失败处理** —— 不要当 `STARTING` 继续等 |
| `STOPPED`(51) / `NOT_FOUND`(60) | **补拉** |
| `FAILED` / `START_FAILED`(1/22) | 先看状态快照与日志定因，再决定是否重拉 |
| **`NEED_REBOOT`(10)** | **重启宿主机后重跑同一条命令**（见 7.10） |

### 7.10 13 线专有：NEED_REBOOT 不是失败

13 线带内核模块补丁（`patches/patch_v4.sh`，hycu.ko）。部署后**需要重启宿主机**才生效。

* 此时状态是 **`NEED_REBOOT`（码 10）**，并带出原因
* **既不是 `FAILED`，也不是 `READY`** —— 调用方不得把它当两者中的任一个处理
* 正确做法：重启宿主机 → **重跑同一条 `start`**
* 驱动补丁一律「改文件 → 重启机器」，**绝不 `rmmod`/`insmod` 重载**
  （重载会让 KFD 驱逐永久打摆、性能塌约 550 倍）

01 线无内核补丁，不会走这条路径。

### 7.11 一线一包

01 线与 13 线**各是一个完整、自包含、可独立交付的包**：

* 包内自带运行所需的**全部**文件：公共文件、线级文件、`@` 元信息、
  状态／日志／Callback 实现、版本材料
* **目标机运行时不依赖**：另一条线的包、源码仓的公共目录、任何事后补拷的脚本

⇒ 把包拷到一台干净机器上解开就能跑完整合同。

### 7.12 版本号怎么读（2026-09-22 起）

```
q38-kit-01 20260922-gcb6a68b-d9ec3c436cf15
           ├─日期──┤ ├─真实HEAD┤ ├─包内容摘要─┤
```

* **`g<7位>`** 是真实的 git HEAD，未伪造
* **`d<12位>`** 是**这一次打进包的内容**的 sha256 摘要 —— 源码未提交时，
  它保证「内容不同 ⇒ 版本不同」

> 为什么需要它：归属证明用 `package_id`（即版本）互证。若两个内容不同的包
> 共用同一版本号，会被误判成同一个包而错误复用或清理。

### 7.13 无参调用等于 start

```bash
bash up.sh                     # ≡ bash up.sh start
bash up.sh GPUS=... PORT=...   # ≡ bash up.sh start GPUS=... PORT=...
```

旧的 `up` / `menu` 同样是 `start` 的别名。**它们都走后台触发，不等待就绪** ——
若你的脚本此前依赖「命令返回即服务可用」，**必须改为轮询 `state`**。

### 7.14 归属是怎么证明的

拉起包**不会**因为容器名字带 `01ma.cli-model-svc-` 前缀就认为它是自己的。
归属要求**标签与快照互证**：

| 来源 | 字段 |
|---|---|
| 容器标签 | `publisher` `package_id` `line` `launch_id` `model_id` `gpus` `port` `launch_mode` |
| 本包快照 | `state/snapshot-<port>.json` 里的 `launch_id` |

证明要求下列四项**同时**精确相等，缺一不可：

| 项 | 须精确等于 | 缺失时 |
|---|---|---|
| `publisher` | `01ma` | 未知归属 |
| `package_id` | 本包 `VERSION` 里的版本串 | 未知归属（**缺失不算通过**） |
| `line` | 本包线号（`01` / `13`） | 未知归属 |
| `launch_id` | **该容器自己端口**的快照 `state/snapshot-<该容器的 port 标签>.json` 的 `launch_id` | 未知归属（无快照亦然） |

容器的端口取自它的**稳定标签 `port`**（不从命令行猜）。按端口查询的 `state` / `stop`
还会额外校验「标签 `port` == 你给的端口」，对不上报 `DETAIL=port_mismatch`。

**任一项缺失或不符 ⇒ 未知归属 ⇒ 失败关闭：不复用、不启动 Worker、不清理、不停止，
交人工处理。** 回报里带 `REASON=` 与 `DETAIL=`（如 `missing_package_id`、
`publisher_mismatch`、`launch_id_mismatch`），照着 `DETAIL` 查是哪一项没对上。

`start` 的复用判定、`state` 的 READY 核验、`stop`、以及唯一的自动清理入口（预清）
四处走的是**同一把尺子**，不存在某处宽某处严。

**换端口（R28）为什么仍然自动。** 旧实例的快照写在**它自己的旧端口**下，
所以证明它属本包要读 `snapshot-<旧端口>.json`，而不是尚未创建的新端口快照。
互证通过后再独立体检新端口：**任意容器占用**或**宿主进程监听**，
只要有一个成立就失败关闭并保留旧服务（`STATE=PORT_BUSY`，带 `HOLDER=`）；
两项都空闲才定点停旧、在新端口上起新的生命周期。

> 旧的按实例名清理（`stage5_cleanup`）在新合同路径（`LAUNCH_ID` 非空）下**不再调用**——
> 它只认名字，证明不了归属。残留的发现与清理改由上述互证逻辑负责。
> 未迁移到新合同的旧调用路径（`LAUNCH_ID` 为空）保持原行为不变。

### 7.15 什么情况下「未知容器」不会挡住你

只有**相关**的未知资源才阻断：占用目标端口、GPU 与本次相交、或其它相关冲突。
**GPU 完全不相交、端口也不同的无关容器，不会因为「不知道它是谁的」就挡住启动。**

**已退出的容器同样挡不住你。** 占用看的是现实事实：只有**正在运行**的容器，
它声明的 GPU 和端口才算数。机器上堆了多少历史 exited 容器、它们当年声明过几张卡，
都与本次启动无关——既不阻断，也不会被本包清理掉。

例外只有一个：**本包自己**的 FAILED 残留（能按 `publisher`/`package_id`/`line`/
快照 `launch_id` 严格互证），即使已退出也会被清掉并换新 `launch_id` 重来。
至于名字撞上了、但归属证明不了的 exited 容器，本包**不会**替你删——
会安全地报错让你自己处置。

端口检查同时看容器与**宿主监听**，所以「容器没声明 `--port` 但进程占着端口」
这种情况也能被发现。

### 7.16 版本号会随文档改动而变

版本是 `<日期>-g<HEAD 短哈希>-d<内容摘要12位>`，其中内容摘要覆盖**包内全部文件**，
`docs/` 下的文档也算。所以**只改文档不改脚本，重建出来的包版本也会变**——
这正是目的：归属互证以版本为据，同版本必须同内容。

反过来，若你改了源码却发现版本摘要没变，说明这次构建根本没把你的改动打进去，
应当停下来查构建，而不是继续发布。

### 7.17 为什么 `start` 有时会「重来一遍」而不是复用

复用看的是**此刻**的事实，不是快照的历史记录：容器必须在运行，健康接口必须通。
服务被 kill、容器崩掉、接口挂死，`start` 都会判为残留，清掉后换新 `launch_id` 重来——
这比回一句「已就绪」然后让你对着一个死服务发请求要好。

启动过程中接口还没通是正常的，不会触发重来。

### 7.18 连着敲两次 `start` 会怎样

第二次会**挂接**到第一次的 `launch_id`，不会再起一个。即使第一次的容器还没建出来
（Worker 正在做体检/S1/打补丁，约几秒的窗口），也挂得上——包会落盘 Worker 的 PID，
并核对 `/proc/<pid>/cmdline` 确实是本包的 Worker，同时要求两次请求的 GPU 集合相同。

如果上一次的 Worker 已经不在了（进程没了、或那个 PID 已被别的程序复用），
包不会一直挂着那个死掉的 `launch_id`，而是新建一个生命周期。
